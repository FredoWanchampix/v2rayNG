# v2rayNG WL — форк для белых списков и устойчивости

👉 **Репозиторий этого форка:** https://github.com/FredoWanchampix/v2rayNG

**Основа и история проекта:**
- Оригинальный клиент: [2dust/v2rayNG](https://github.com/2dust/v2rayNG) — оригинальный клиент, который стабильно развивается и служит источником синхронизации.
- Предыдущий форк: [elizqmill/v2rayNG](https://github.com/elizqmill/v2rayNG) — автор начал эту работу первым и заложил основу, на которой вырос этот проект.
- Этот форк берёт **изменения и идеи из обоих репозиториев**: благодарю авторов за вклад и сохраняю атрибуцию и преемственность.

Android-клиент V2Ray/Xray на базе [v2rayNG](https://github.com/2dust/v2rayNG), доработанный под три цели:

1. **Работа в сетях с «белыми списками»** — там, где пинг проходит до любого адреса, но скорость на неразрешённых IP искусственно режется шейпингом, а обычная проверка задержки ничего не показывает.
2. **Устойчивость соединения в ограничительных сетях** — периодические обрывы TLS-рукопожатий не роняют обновление подписок и загрузку конфигов.
3. **Расширенный набор протоколов и ядер** — помимо штатных VLESS/VMess/Shadowsocks/Trojan/WireGuard/Hysteria2/MASQUE добавлены Hysteria v1, AmneziaWG, NaiveProxy, OpenConnect/AnyConnect, Mimic и FPTN через сайдкар-движки (mihomo, sing-box, mimic-client, fptn-client).
4. **Полнота переноса настроек** — конвертеры подписок и шаринг не теряют контекст: шум DPI-защиты WireGuard, обфускация AmneziaWG, obfs Hysteria2, транспорты, DNS туннеля, certificate pinning; длинные ссылки передаются сегментированными QR без сжатия и сокращений.

**Ключевые слова:** Android VPN, V2Ray, Xray, sing-box, mihomo, Hysteria, Hysteria2, NaiveProxy, OpenConnect, AmneziaWG, Mimic, FPTN, MASQUE, WARP, WireGuard noise, DPI-шум, сегментированный QR, белые списки, DPI, прокси, подписки, certificate pinning, встроенный загрузчик обновлений, докачка, многопоточная загрузка.

## Чем этот форк отличается от оригинала

### 1. Поиск стабильных профилей (проверка по белым спискам)

Главный экран → ⋮ → **«Поиск стабильных профилей (проверка БС)»**.

Проверка идёт в два этапа:

1. у всех профилей измеряется реальная задержка через ядро;
2. каждый живой профиль дополнительно проверяется **скачиванием тестового файла** через собственное временное ядро — именно это вскрывает шейпинг белого списка, который не виден по пингу.

Рядом с пингом отображается измеренная скорость:

| | |
|---|---|
| 🟢 `3.4 MB/s` | профиль полностью пригоден |
| 🟠 `420 KB/s` | скорость понижена, но пользоваться можно |
| 🔴 `18 KB/s` | шейпинг белого списка |

- Пинг при проверке скорости **не перезаписывается**.
- У каждого проверенного профиля сохраняется числовое значение скорости.
- Меню ⋮ → **«Сортировать по скорости»**.
- Профили со скоростью `0 кБ/с` удаляются отдельным действием (**«Удалить нулевые»**).

Настраиваемые параметры этапа (Настройки → «Поиск по белым спискам»): количество целевых профилей, таймаут TCP-пинга, размер тестового файла, таймаут скачивания, число прогонов.

### 2. Устойчивость к обрывам TLS

- **Trust-all TLS для служебных загрузок:** проверка сертификатов отключена для загрузки подписок, проверки обновлений и скачивания geo-файлов — в ограничительных сетях middlebox'ы рвут рукопожатия (`SSLHandshakeException: connection closed`).
- **6 попыток загрузки подписки** с экспоненциальным backoff (`min(1500·attempt, 6000)` мс); ретраятся `IOException`/`SSLException`. Одна сброшенная рукопожатие больше не роняет всё обновление подписки.
- **Проверка обновлений через активный профиль** — общий резолвер маршрута решает по состоянию ядра, а не одним TCP-пробником порта: если профиль работает и слушает loopback HTTP inbound, запрос идёт через него (логин/пароль читаются из runtime-конфигурации туннеля). Если профиль работает, но loopback inbound не поднят, запрос явно отклоняется с инструкцией включить локальный прокси — direct-запрос бы обошёл профиль, ведь приложение исключает себя из собственного туннеля.
- **Обновление гео-файлов через активный профиль** — кнопка скачивания открывает меню «Обновить» / «Обновить через активный профиль», работающее в тех же режимах VPN / hev-tun / root / FPTN и использующее тот же резолвер маршрута.

### 3. Конвертеры подписок

В настройках каждой подписки доступны переключатели:

- **Base64 в текст** — разворачивает base64-тело подписки в обычный список ссылок.
- **Кастомные в ссылки** — преобразует JSON-профили в обычные ссылки (`vless://`, `vmess://`, `ss://`, `trojan://`, `hysteria2://`, `tuic://` и др.), редактируемые штатным интерфейсом.

Поддерживаются xray-outbounds, sing-box формат и полные конфиги построчно. Нераспознанные записи сохраняются как кастомные профили (без потери исходного JSON — при экспорте они выгружаются как есть).

Автоматическая обработка **SHA-256 certificate pinning**: при включённой опции подписки профили с заполненным `pinSHA256`/`pinnedCA256` помечаются `insecure`, чтобы pin не ломал соединение.

Свитч **«Автополучение отпечатка сертификата»** дополняет её: при обновлении или добавлении подписки профили, у которых отпечатка ещё нет, получают его автоматически — той же функцией, что стоит за кнопкой «Получить отпечаток сертификата» в редакторе профиля (TLS-рукопожатие; Hysteria v1/v2 — QUIC-рукопожатие). Сертификат, пришедший вместе с подпиской, приоритетнее и **никогда не перезаписывается**; неподдерживаемые протоколы (wireguard, ss, socks, reality и др.) не опрашиваются; одинаковые эндпоинты (протокол+адрес+порт+SNI+ALPN) опрашиваются один раз на обновление. Порядок применения строгий: сначала получение отпечатков, затем авто-`insecure` — чтобы свежий отпечаток тоже был учтён. Сбой получения на одном профиле не мешает ни остальным профилям, ни сохранению подписки.

Само TLS-рукопожатие ради отпечатка выполняется **без проверки цепочки сертификатов** (trust-all, как все служебные загрузки форка): смысл операции — зафиксировать сертификат сервера, каким бы он ни был, а доверие появляется позже, когда ядро сверяет отпечаток каждого соединения с сохранённым. Иначе рукопожатие ломалось в двух реальных случаях: системный MITM-анализ трафика с пользовательским CA (Android-приложения не доверяют пользовательским CA) и самоподписанные сертификаты серверов. Формат результата — 64 строчных hex SHA-256 от DER leaf-сертификата, побайтово совпадает со значением нативной функции.

Свитч **«Получать отпечатки через включённый профиль»** направляет эти рукопожатия через loopback HTTP-прокси запущенного профиля — так же, как обновление подписки, проверка обновлений клиента, загрузчик обновлений и geo-файлы. Это обязательно в ограничительных сетях: прямое TLS-рукопожатие к зарубежному серверу там обрывается (reset) или висит до таймаута, а то же рукопожатие через профиль проходит. Если свитч включён, а пригодного маршрута нет (профиль не запущен, либо запущен без loopback-прокси и это не системный TUN), отпечатки **не получаются вовсе** и в логе остаётся явная причина: идти напрямую означало бы обойти профиль и риск записать подменённый сертификат. Профиль-системный TUN (FPTN) считается корректным маршрутом: приложение находится внутри туннеля, поэтому прямое соединение физически идёт через профиль.

Запрос CONNECT отправляется **ровно тем адресом, который записан в профиле** (`server`), — доменом, если профиль доменный, и IP, если профиль по IP. Подменять адрес на SNI нельзя: у профилей с IP-адресом `sni` часто является маскирующим доменом чужого хоста (`server=104.21.7.43`, `sni=…workers.dev`), и запрос ушёл бы не на тот сервер. Домен предпочтительнее там, где он есть: при CONNECT по IP ядро восстанавливает домен сниффингом ClientHello и применяет к нему свои правила маршрутизации (вещдок: `CONNECT [178.176.128.203:443]` → `sniffed domain: media.ipcheak.online` → `taking detour [block]`).

Прямого запасного пути при включённом свитче **нет — намеренно**. Через профиль снимается настоящий сертификат сервера (вещдок 20.11.2026: issuer `Google Trust Services` / `Let's Encrypt`), потому что соединение идёт тем же путём, каким работает сам профиль. Напрямую сертификат может быть подменён системным анализатором трафика: тот же сервер `104.21.7.43:2053` напрямую вернул сертификат с issuer `AdGuard Personal Intermediate`. Записанный в профиль отпечаток перехватчика не совпал бы с тем, что ядро увидит при работе, и pinning сломал бы подключение. Поэтому при неудаче отпечаток не записывается вовсе, а в логе остаётся явная причина с перечнем сделанных попыток. Если нужен именно прямой путь — выключите свитч: маршрут `direct`, как и прежде.

QUIC-рукопожатия (Hysteria v1/v2) через HTTP-CONNECT не туннелируются и всегда идут напрямую — их UDP в таких сетях проходит и так. В логе при этом указывается фактический маршрут (`via direct`), а не выбранный свитчом.

Конвертер покрывает **все протоколы форка**: для каждого JSON-профиля либо собирается ссылка (`vless://`, `vmess://`, `ss://`, `trojan://`, `hysteria://`, `hysteria2://`, `socks://`, `wireguard://`, `masque://`, `awg://`, `naive://`, `openconnect://`, `mimic://`), либо профиль остаётся кастомным **с явной причиной в логе**. Явные отказы: `tuic` (парсер ссылок в форке отключён), `http` (схема не импортируется, а для приватного IP строка ушла бы в подписку), `fptn` (собственный TUN, нет Xray-outbound), группы/цепочки (`policygroup`, `proxychain`), multi-peer/multi-server/multi-user outbound, нестандартный allowedIPs wireguard, vmess/trojan xhttp (формат ссылки не выражает mode/extra у vmess v2), ss-плагин кроме obfs=http, recv-window у hysteria v1 (схема ссылки не выражает). Молчаливых потерь нет: если хотя бы один outbound мульти-серверного конфига не конвертируется, конфиг сохраняется целиком. AmneziaWG-опции (jc/jmin/jmax/s1–s4/h1–h4/i1–i5/version) переносятся в `awg://` один-в-один — конвертация в plain `wireguard://` с потерей обфускации запрещена. Переносятся также: obfs Hysteria2 (salamander/gecko, включая packetSize из finalmask), транспорты vless/vmess/trojan (ws/kcp/grpc/h2/xhttp), host-массивы и alpn-списки целиком, DNS туннеля из глобальной секции `dns` конфига в `remoteDNS` wireguard, certificate pinning и uTLS-fingerprint.

#### Шум (DPI-защита) WireGuard

Шумовые пакеты перед handshake маскируют WireGuard от DPI. В форке шум — **опциональное поле wireguard-профиля, доступное во всех точках входа**:

- **Редактор**: выпадающий список пресетов («AmneziaWG: 4 мусорных пакета 40-70», «Шум под QUIC», «WARP: hex + 8 случайных 23-911») и человекочитаемое поле списка шумов (JSON-массив `[{"rand":"23-911","delay":"1-3"}]` или типизированные пакеты `{"type":"hex|str|base64|exp","packet":"...","delay":"1-3"}`).
- **Импорт из буфера**: ссылка `wireguard://…&fm=…` (полный FinalMaskObject) и/или `&noises=…` (явный список) полностью восстанавливает шум в поле профиля. Старые ссылки только с `fm` тоже заполняют поле.
- **Конвертер подписок**: цепочка «wireguard → freedom(noises)» поглощается в `fm`/`noises` без потери защиты (ядро Xray v26.11.9 применяет `streamSettings.finalmask.udp` к wireguard напрямую); собственный `finalmask` wireguard-outbound переносится как есть.
- **Экспорт/шаринг**: `toUri` включает и `fm`, и `noises` — «весь контекст» передаётся целиком.

Хранение: новое поле `ProfileItem.noisesJson` синхронно с noise-частью старого `finalMask` (обратная совместимость сохранена). Применение: `streamSettings.finalmask.udp[{type:"noise",settings:{noise:[…]}}]`. Очистка поля шума действительно убирает шум; невалидный список отклоняется при сохранении, а не теряется молча.

**Опциональность — жёсткий инвариант.** Шум и обфускация AmneziaWG — надстройки, а не обязательные части профиля:

- профиль **без** шума (и без обфускации) полностью работоспособен: plain WireGuard, в ссылке нет ни `fm`, ни `noises`, в конфиге нет `finalmask`;
- очистка поля шума в редакторе **действительно убирает** защиту, профиль сохраняется и работает без неё;
- повреждённый ключ `noises` в ссылке **не блокирует импорт**: профиль импортируется с `fm` как есть (шум восстановится из валидного `fm`); битый список в редакторе отклоняется при сохранении только чтобы не записать мусор вместо защиты — владелец всегда может очистить поле и сохранить профиль без шума;
- wireguard-конфиг **без** `amnezia-wg-option` конвертируется в plain `wireguard://`; `awg://` без опций не создаётся (бессмысленна), но и не блокирует профиль.

Ни один код не вправе навязать шум или обфускацию профилю, который их не имел.

#### QR-экспорт и импорт без сжатия и сокращений

Один QR-код физически вмещает не более 2953 байт (ISO/IEC 18004, версия 40, byte mode) — «QR нового типа» с большей ёмкостью не существует. Поэтому длинные ссылки (wireguard с шумом, vless с большим finalmask — тысячи байт) передаются **последовательностью обычных QR**: протокол `V2NGQR1|<id>|<idx>|<cnt>|<crc32>|<chunk>`, где `chunk` — целый читаемый кусок исходной ссылки без каких-либо преобразований, `idx/cnt` — номер и количество, `crc32` — контрольная сумма всей ссылки.

- **Экспорт**: диалог-пейджер «QR n из N»; свайп между кодами. Короткая ссылка (≤ 2800 байт) остаётся одним обычным QR без префикса — сторонние сканеры работают как раньше.
- **Импорт**: камера **и** выбор файла-скриншота; сегменты принимаются в любом порядке, дубликаты идемпотентны, чужая серия сбрасывает накопленное; прогресс — тост «Получен сегмент n из m»; по завершении CRC32 проверяет целостность и полная ссылка уходит в обычный импорт.
- Эмодзи и прочие суррогатные пары не рвутся границей куска.
- Никакого сжатия, base64-упаковки payload и сокращений ссылок: каждый QR человек может прочитать и проверить глазами.

### 4. Дополнительные протоколы и сайдкар-движки

Форк добавляет протоколы, которых нет в оригинале. Они работают через **сайдкар-движки** — отдельные исполняемые процессы, поднимающие локальный mixed-порт (SOCKS/HTTP), который Xray-ядро использует как восходящий прокси:

| Протокол | Движок | Как подключается |
|---|---|---|
| **AmneziaWG** | `mihomo` (MetaCubeX) | wireguard-outbound с `amnezia-wg-option` (jc/jmin/jmax/s1–s4/h1–h4/i1–i5 и пр.) |
| **Hysteria v1** | `mihomo` (MetaCubeX) | hysteria-outbound (auth_str, up/down, obfs, sni, alpn, ports, recv-window, lazy-start); Xray форка не имеет v1, sing-box собран без QUIC |
| **NaiveProxy** | `sing-box` | naive-outbound |
| **OpenConnect / AnyConnect** | `sing-box` | endpoint + rule-route |
| **Mimic** | `mimic-client` | Hysteria2-семейство (MTP + TLS-мимикрия), домены мимикрии |
| **FPTN** | `fptn-client` | отдельный TUN в **root-режиме** (см. примечание ниже) |

> **FPTN:** клиент создаёт и владеет собственным TUN-интерфейсом, поэтому заменяет весь стек Xray + hev-tun и работает **только в root-режиме** (Android выделяет единственный VPN-слот). Бинарник `fptn-client` кросс-собирается в CI через Conan+NDK.

#### Где физически лежат движки и почему не в `assets/`

Все движки упакованы как `lib*.so` в `V2rayNG/app/libs/<abi>/` и исполняются из `nativeLibraryDir`:

| Движок | Файл в APK | Обслуживает |
|---|---|---|
| mihomo | `lib/<abi>/libmihomo.so` | AmneziaWG (wireguard + `amnezia-wg-option`), **Hysteria v1** (hysteria-outbound: auth_str, up/down, obfs, sni, alpn, ports, recv-window, lazy-start) |
| sing-box | `lib/<abi>/libsingbox.so` | NaiveProxy (naive-outbound), OpenConnect/AnyConnect (endpoint + rule-route) |
| mimic-client | `lib/<abi>/libmimicclient.so` | Mimic (Hysteria2-семейство: MTP + TLS-мимикрия, домены мимикрии) |
| fptn-client | `lib/<abi>/libfptnclient.so` | FPTN (собственный TUN, root-режим) |
| dnsproxy | `lib/<abi>/libdnsproxy.so` | DNS-форвардер пробы FPTN (upstream из настроек пользователя: udp/tcp/tls/https/quic/sdns) |
| speedprobe | `lib/<abi>/libspeedprobe.so` | замер скорости/задержки внутри изолированного netns (проба FPTN) |

Причина переноса из `assets/` **жёсткая, а не стилистическая**: на Android 10+ политика SELinux (W^X) запрещает домену `untrusted_app` исполнять файлы с контекстом `app_data_file` (то есть из `filesDir`) и `shell_data_file` (`/data/local/tmp`) — `execve` возвращает `EACCES`. `nativeLibraryDir` имеет контекст `apk_data_file`, исполнение оттуда разрешено и приложению, и root. Поэтому установка движка в `assets/` + копирование в `filesDir` + запуск оттуда на Android 10+ **не работает вообще**: ни один сайдкар-протокол не запустился бы. Тот же паттерн форк уже применял для `libhevsockstun.so` в root-режиме.

Механизм: имя файла обязательно начинается с `lib` и заканчивается на `.so`, тогда PackageManager извлекает его из APK в `nativeLibraryDir`; извлечение включено `packaging.jniLibs.useLegacyPackaging = true` (`extractNativeLibs=true`). Если поставить `false`, библиотеки останутся внутри APK несжатыми и запустить их как отдельный процесс станет невозможно.

Данные (конфиги, логи, pid-файлы) при этом остаются в `filesDir/engines/` — запись туда разрешена, запрещено только **исполнение**.

#### Архитектуры

Движки собираются под все четыре ABI приложения: `arm64-v8a`, `armeabi-v7a`, `x86`, `x86_64`. Gradle ABI-splits кладут в каждый APK движки **его собственной** архитектуры, а `universal` содержит все четыре набора. Нюанс кросс-сборки Go под Android: `CGO_ENABLED=0` работает только для `arm64`, а для `android/arm`, `android/386` и `android/amd64` сам Go требует внешнюю линковку (`android/<arch> requires external (cgo) linking`), поэтому эти ABI собираются с `CGO_ENABLED=1` и NDK-clang. CI проверяет каждый бинарник по ELF-заголовку и списку `DT_NEEDED`, а `libc++_shared.so` не допускается ни в одном движке.

Движки собираются в GitHub Actions одним общим действием `.github/actions/bundle-sidecar-engines` (mihomo — официальный prebuilt четырёх ABI, sing-box — из исходников с CGO+NDK clang для naive/cronet, Mimic — кросс-компиляция Go, FPTN — Conan+NDK, dnsproxy и speedprobe — отдельные reusable-workflow со своими версиями Go). Общий бандлинг используется и в `build.yml`, и в `build-upstream-master.yml`, поэтому APK из релизной и из sync-сборки идентичны по составу движков.

#### Как измеряются FPTN-профили (изолированный netns)

FPTN-профиль нельзя измерить обычным способом: `fptn-client` создаёт собственный TUN-интерфейс и владеет им, а JVM приложения физически не видит чужой TUN. Поэтому замер выполняется **в изолированном network namespace**:

1. Root-скрипт создаёт netns и veth-пару, настраивает NAT и два правила маршрутизации. Правила именно **два**: одно для ответного трафика (`ip rule ... lookup main`) и одно для исходящего (`fwmark` → таблица активного физического интерфейса). В Android маршрут по умолчанию лежит в таблице интерфейса, а не в `main`, поэтому без маркировки исходящий трафик netns попал бы на catch-all `unreachable` и интернет внутри netns не появился бы.
2. Активный физический интерфейс определяется с **обязательным исключением tun-интерфейсов** (`utun`, `tun`, `fptn`, `wg`, `ppp`) — иначе при работающем VPN проба полезла бы туннелем поверх туннеля.
3. Внутри netns поднимается `dnsproxy`, слушающий на `127.0.0.1:53`, и `fptn-client` со своим пробным TUN.
4. Замер выполняет `speedprobe`: скорость (несколько попыток, размер файла и таймауты — из настроек приложения) и задержку как TTFB. Системный `curl` использовать нельзя: он не входит в toybox и появился только с Android 8.0, а `minSdk` приложения — 24.
5. По завершении пробные процессы убиваются **только** по своим pid-файлам и только после тройной проверки: cmdline содержит уникальный маркер этой пробы, inode сетевого пространства совпадает с ожидаемым, и лишь затем `TERM` → `KILL`. `pkill` по имени бинарника применять нельзя: PID namespace в Android общий, и он убил бы основной рабочий профиль.

**Почему нужен именно `dnsproxy`, а не `nameserver` в `resolv.conf`:** внутри netns системный резолвер Android возвращает fake-IP активного VPN (диапазон `198.18.0.0/15`), то есть адреса, маршрутизируемые в чужой туннель. Кроме того, DNS пользователя может быть задан как DoQ/DoT/DoH (например `quic://94.140.14.14:853`), чего `resolv.conf` не понимает вовсе. `dnsproxy` форвардит запросы на **upstream из настроек пользователя как есть** — поддерживаются все пять транспортов: `udp://`, `tcp://`, `tls://`, `https://`, `quic://` и `sdns://`. Никакого хардкода DNS-провайдеров нет: берутся ровно те серверы, что указаны в настройках.

Тонкости, которые иначе ломают замер молча:

- `SSL_CERT_DIR` обязан указывать на `/apex/com.android.conscrypt/cacerts`. Монтирование `tmpfs` на `/etc` скрывает всё содержимое `/system/etc` (поскольку `/etc` — симлинк на него), включая системное хранилище CA-сертификатов. Без этого DoQ/DoT/DoH падают с «certificate signed by unknown authority», `dnsproxy` отвечает SERVFAIL, а замер тихо даёт ноль.
- Файл `/etc/hosts` обязателен: без него `dnsproxy` завершается сразу при старте.
- `--exclude-tunnel-networks` у `fptn-client` **заменяет** встроенное значение (`10.0.0.0/8, 192.168.0.0/16`), а не дополняет его. Поэтому список формируется как дефолт + подсеть veth-пары + IP DNS-эндпоинтов. Иначе теряется обход LAN, а DNS уходит в туннель — замер начинал бы измерять сам себя, и при сбое туннеля DNS умирал бы вместе с ним.
- Одновременно выполняется **не более одной** FPTN-пробы: правила маршрутизации с фиксированными приоритетами, общие цепочки iptables и флаг `ip_forward` не допускают параллельности.

### 5. Расширенная диагностика

- TCPing, real ping и **ICMP ping** — из меню главного экрана.
- Отображение задержки до IP-lookup; показ соединения до резолва.
- Расширенное редактирование Hysteria2: выбор obfs (`none`/`salamander`/`gecko`), размеры пакетов для gecko, кнопка получения certificate pin.

## Полнота синхронизации с апстримом

Синхронизация выполняется workflow `Sync upstream and build v2rayNG` **только вручную** (`workflow_dispatch`). Автоматических запусков по расписанию и по push нет: слияние апстрима может затронуть уникальные функции форка и поэтому всегда выполняется под контролем владельца.

- строгий merge без «тихого» подавления конфликтов — любой неразрешённый конфликт останавливает job и **не трогает master**;
- шаг эквивалентности проверяет, что все файлы, изменённые только апстримом, остались байт-в-байт как в апстриме;
- перед публикацией создаётся резервная ветка предыдущего master;
- каждый релиз содержит **список изменений именно этого релиза** (см. ниже).

## История релизов

Каждый релиз публикует список изменений **относительно предыдущего опубликованного релиза**, а не накопительный дубликат. Предыдущий тег определяется по **времени публикации релиза**, а не лексикографической сортировке имён тегов, поэтому в notes попадают только реально новые коммиты:

- **Коммиты форка** — изменения самого форка с прошлого релиза;
- **Коммиты upstream** — коммиты апстрима, интегрированные этим слиянием.

## Сборка

Сборка APK выполняется GitHub Actions **только по явному запуску** — пуши в master сами по себе ничего не собирают (устранено дублирование сборок). Workflow готовит Android SDK/NDK, собирает native-библиотеки (hev-socks5-tunnel), скачивает `libv2ray.aar`, затем общее действие `bundle-sidecar-engines` готовит все шесть движков под все четыре ABI, и только после этого собирается APK для всех ABI + universal и **блокирующим образом** выполняются unit-тесты.
Релиз появляется только при явно выбранном канале: `stable` — стабильный релиз, `prerelease` — бета, `none` — только сборка и проверка. Подпись релизов выполняется только ключом владельца из GitHub Secrets; debug-подпись допускается исключительно для канала `none`, который ничего не публикует.
Все шесть движков (`mihomo`, `sing-box`, `mimic-client`, `fptn-client`, `dnsproxy`, `speedprobe`) проходят жёсткую проверку до сборки APK: наличие файла в `libs/<abi>/`, соответствие класса и архитектуры ELF целевому ABI, сверка контрольных сумм артефактов с манифестом продюсера и сверка списка `DT_NEEDED` с ожидаемым для каждого движка. Отсутствие или повреждение любого движка останавливает сборку, а не проходит молча.

### 4. Встроенный загрузчик обновлений

В разделе «Проверка обновлений» есть переключатель **«Скачивать через встроенный
загрузчик»** (по умолчанию выключен — кнопка «Скачать» открывает ссылку релиза в
браузере, как раньше). При включении обновление скачивается внутри клиента:

- **Многопоточная загрузка**: файл делится на сегменты (настраивается, 1–24
  потока), каждый сегмент качается своим соединением и дописывается в свой
  part-файл; по завершении сегменты склеиваются в один APK.
- **Докачка с того же байта** при обрыве связи, смене сети (Wi-Fi ↔ мобильная),
  режиме полёта, убийстве процесса и перезагрузке устройства: HTTP Range
  (RFC 9110), валидация продолжения по ETag/Last-Modified (смена объекта на
  сервере ведёт к честному рестарту), состояние хранится в MMKV и переживает
  перезапуск; после загрузки система возобновляет докачку автоматически.
  Докачка доступна сколь угодно долго: подписанный CDN-URL GitHub живёт около
  часа и не сохраняется — каждый сегментный запрос идёт по постоянной ссылке
  релиза и получает свежий редирект.
- **Стабильность на плохих сетях**: переходящие ошибки (обрывы, 5xx, 429)
  ретраятся без лимита с паузами; при потере сети загрузка ждёт её возвращения,
  а не отменяется. Скачанное при отмене НЕ удаляется — следующее «Скачать»
  продолжит докачку.
- **Целостность**: стриминговый SHA-256 во время склейки сверяется с
  `SHA256SUMS.txt` того же релиза (плюс сверка размера с манифестом релиза и
  Content-Type ответа). Непроверенный файл никогда не предлагается к установке;
  при несовпадении part-файлы удаляются и предлагается повтор.
- **Прогресс в уведомлении**: процент, скорость (Б/КБ/МБ/ГБ в секунду,
  обновление раз в секунду) и остаток времени; кнопки Пауза / Продолжить /
  Отмена работают из шторки и с экрана.
- **Установка**: после проверки открывается системный установщик через
  FileProvider. Автозапуск установки — только пока пользователь внутри клиента;
  если клиент свёрнут или закрыт, в уведомлении остаётся кнопка «Установить».
- **Маршрут**: переключатель «Проверять и скачивать через активный профиль»
  направляет и проверку, и загрузку через loopback-прокси запущенного ядра
  (тот же резолвер маршрута, что у подписок); если профиль выключился во время
  загрузки, загрузка останавливается с понятным сообщением, а не уходит в
  бесконечные ретраи через мёртвый прокси.
- **Каталог**: `Download/<имя приложения>/` (part-файлы, готовый APK и лог
  `update_download.log`), создаётся штатными средствами без root; при
  недоступности публичного каталога используется приватный каталог приложения.

Загрузчик не использует WebView и системный DownloadManager: только собственный
HTTP-клиент приложения.

## Каналы обновлений и подпись

- **Стабильный канал** — GitHub помечает релиз как Latest; приложение с выключенным переключателем «Проверять предварительные версии» видит только его.
- **Предварительный канал** — бета публикуется с флагом prerelease и не сдвигает Latest; приложение видит её только при включённом переключателе предварительных версий.
- Бета всегда получает версию выше установленной стабильной, иначе сравнение версий не предложило бы обновление.
- Беты **одной и той же версии** (например две сборки `2.4.2-beta.…`) приложение различает по коммиту: в APK вшивается `BuildConfig.GIT_COMMIT`, а релиз несёт `target_commitish`; при равенстве versionName обновление предлагается, если коммит релиза отличается от коммита установленного APK. Переключатель «Проверять предварительные версии» включает учёт бет.
- Релизные APK подписываются ключом владельца, который хранится только в GitHub Secrets. В публичный репозиторий и артефакты keystore не попадает.
- Для каждого релиза проверяются подпись APK (схемы v1+v2+v3 внутри APK и v4 в парном файле `.idsig`), соответствие `versionName` тегу, наличие всех шести движков во всех ABI и успешные unit-тесты.

## Установка

Скачайте нужный APK из последнего релиза:

- `arm64-v8a` — 64-бит ARM (большинство телефонов с 2017 г.);
- `armeabi-v7a` — 32-бит ARM;
- `x86_64` / `x86` — эмуляторы;
- `universal` — любая архитектура: содержит наборы движков для всех четырёх ABI, поэтому заметно больше по размеру.

Каждый APK содержит движки **своей** архитектуры; скачивать «про запас» чужой ABI не нужно.

Рядом с каждым APK публикуется парный файл `.idsig` — это подпись схемы v4, которая физически не хранится внутри APK. Скачайте оба файла в одну папку: тогда `apktool` и `apksigner` покажут все четыре схемы подписи (V1 + V2 + V3 + V4).

Проверьте контрольные суммы в `SHA256SUMS.txt`.
